# セキュリティテストレポート

Week8課題「会員制ブログ」「匿名掲示板」に対して、以下の3つの攻撃に対する耐性をテストしました。

## 1. XSS(クロスサイトスクリプティング)対策

### テスト内容
匿名掲示板の投稿欄に、以下のスクリプトを入力して投稿した。

### 結果:合格

投稿は正常に保存され、一覧画面に表示されたが、スクリプトは実行されず、
タグがそのまま文字列として画面に表示された。
アラート(ポップアップ)は一切表示されなかった。

### 理由
Bladeテンプレートの `{{ }}` 構文が、出力時に自動的にHTMLエスケープを行っているため。
`<script>` タグが `&lt;script&gt;` に変換され、ブラウザがタグとして解釈しなかった。

---

## 2. CSRF(クロスサイトリクエストフォージェリ)対策

### テスト内容
ブラウザの開発者ツール(Network タブ)を使い、投稿フォーム送信時の送信データを確認した。

### 結果:合格

送信データの中に `_token` という項目が含まれており、
ランダムな文字列(CSRFトークン)が正しく送信されていることを確認した。

### 理由
全てのフォームに `@csrf` ディレクティブが記述されており、
Laravelの `VerifyCsrfToken` ミドルウェアが、トークンの正当性を検証しているため。
トークンが一致しない場合、リクエストは自動的に拒否される。

---

## 3. SQLインジェクション対策

### テスト内容
ログインフォームのメールアドレス欄に、以下の文字列を入力してログインを試みた。

ブラウザ標準のメール形式バリデーションにより送信自体がブロックされたため、
コードレビューによる検証も合わせて実施した。

### 結果:合格

以下のコマンドで、コントローラー・モデル内に生SQL(DB::select、DB::raw、whereRaw)が
使用されていないことを確認した。

```bash
grep -rn "DB::select\|DB::raw\|whereRaw" app/Http/Controllers/ app/Models/
```

→ 該当なし(何も検出されなかった)

### 理由
全てのデータベース操作がEloquent ORM(例: `User::where('email', $email)`)経由で
行われており、Eloquentは内部で自動的にプリペアドステートメントを使用するため、
入力値がSQL文の構造に影響を与えることはない。

---

## テスト結果まとめ

| 項目 | 結果 |
|---|---|
| XSS対策 | ✅ 合格 |
| CSRF対策 | ✅ 合格 |
| SQLインジェクション対策 | ✅ 合格 |

3つの主要な攻撃パターンに対して、Laravelの標準機能(Bladeの自動エスケープ、
